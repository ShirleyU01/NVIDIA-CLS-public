What a student does

One device, two kinds of session.

Oral exams show understanding that a multiple-choice form misses. They also do not scale, and a model score with no source is not something a teacher can stand behind. Socrates splits that problem into a high-stakes spoken exam and a lower-stakes study loop.

Oral exam

The proctor conducts the exam out loud. The session is the record: video, a timestamped transcript, and screenshots.

  1. The device speaks the question with Piper, a local text-to-speech voice.
  2. The student answers. faster-whisper transcribes on the Jetson, with a short domain prompt so technical terms survive.
  3. The proctor can ask a follow-up, then move on.
  4. The camera can grab the moment the student points at written work.
  5. The finished folder — recording, transcript, images — is what grading reads.

Study mode

Practice, not a recorded exam. The student works on paper, shows the page, and gets feedback before the session ends.

  1. Pick a course, a topic, and how many questions. The bank selects ones this student has not already seen.
  2. Solve it on paper. Frame the page. Up to five captures per question.
  3. A vision model reads the writing and returns feedback the student can see immediately.
  4. An “ask me anything” tutor stays on that problem, including the math.
  5. Ending the run writes three things: takeaways, what to improve, and a next step. The teacher dashboard reads the same run.

How it is put together

Four parts. The session is the object they share.

Course material becomes a question. The Jetson runs the session. A central service keeps rubrics, students, and reviews. A separate pipeline turns the session into a packet a person can audit.

01

Question bank

Lecture and exam PDFs are parsed, chunked without a model, embedded in FAISS, and retrieved by topic. Generation and evaluation are later stages, checkpointed on disk, so a failed question does not force the course to be parsed again. The export is the flat exam JSON the proctor already knows how to ask.

02

Jetson runtime

A local FastAPI service drives the student UI. Speech-to-text, text-to-speech, and the camera sit next to the person taking the exam. Session files are written on the device: recording, transcript, paper photos, and study metrics.

03

Central API and web app

FastAPI and SQLite hold rubrics, assessments, student identity, question history, and session status. One React app serves both roles: the student flow on the device, and a teacher console for assessments, session detail, study metrics, and a written review with final scores and comments.

04

Evidence packet

Given a rubric and a normalized session, the pipeline asks a model to score each criterion and attach evidence. The model is swappable. The checks underneath it are not. The teacher’s review is stored beside the packet, so the model draft and the human decision stay distinct.

The part worth walking through

The model proposes. The code decides what is allowed to stand.

An unconstrained grader can invent a quotation. Socrates treats the model output as untrusted until it survives a deterministic pass over the session that actually happened.

  • A quote has to occur. Every transcript quote must be an exact substring of a student answer. A paraphrase is a flag, not evidence.
  • A time has to exist. A timestamp must match a screenshot from that session, or both ends are null and the missing time is flagged.
  • A positive score needs support. If the score is above zero and the evidence list is empty, the item is flagged score_without_evidence.
  • Confidence is a number in range. Anything outside 0 to 1 is rejected as a flag, not quietly clamped.

From a syllabus to a question the device can ask

The course is a pipeline, not a prompt.

The bank was built against a probability course, CS109: lectures, exams, and review notes. Each stage writes a checkpoint. Embeddings are a FAISS index plus a sidecar of chunk metadata, so a later vector database can replace the index without rewriting generation.

Why this is the project to show

It is a system, and the risky part is checked.

A company reading this should see three decisions, not a feature list. The interaction runs on the device, because an oral exam is a camera, a microphone, and a person in the same room. The durable record is separate, because teachers, rubrics, and reviews outlive one Jetson. And the model is not the grader of record: it proposes a score, and ordinary code checks whether the evidence is real.

The surface area matches that. There is a student flow and a teacher flow in one web app, a runtime for the spoken exam, a study loop with paper capture and a tutor, a question bank with stages you can rerun, and tests around the packet, the study feedback, and the bank.

We built it as a team of four in Stanford CS210A/B, with NVIDIA as the collaborating company. Study mode was then piloted in Stanford CS109 with 50+ students across 89 sessions. NVIDIA gave the project its award at the end of the quarter.

The public repository is the code and the course materials. Student sessions and recordings are not in it.
